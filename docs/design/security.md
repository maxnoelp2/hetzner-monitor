# Design: Security

Status: encryption & auth **accepted** ([ADR-0005](../adr/0005-envelope-encryption-for-secrets.md), [ADR-0007](../adr/0007-auth-sessions-and-api-keys.md)); sessions, CSRF, throttling and key rotation **implemented** (M5a, [ADR-0013](../adr/0013-sessions-csrf-and-key-rotation.md)); web UI headers **implemented** (M6a, [ADR-0015](../adr/0015-web-ui-embedded-in-binary.md))

## Threat model (short)

The database holds API tokens for other people's infrastructure. Assume: DB dumps leak, logs get
shared in bug reports, webhook targets are attacker-controlled (SaaS). Protect tokens first.

## Envelope encryption for secrets at rest

Applies to Hetzner tokens, notification channel configs (Slack/Discord webhook URLs are secrets too), push
subscriptions (endpoint and keys) and the installation's VAPID private key ([ADR-0017](../adr/0017-web-push.md)).

1. Generate a random 256-bit **DEK** per row.
2. `secret_ct = AES-256-GCM(DEK, nonce₁, secret, AAD = row id)`
3. `dek_ct = AES-256-GCM(master_key[key_version], nonce₂, DEK, AAD = row id)`
4. Store `secret_ct`, `dek_ct`, `key_version`. Nonces are random 96-bit and prefixed to the ciphertext.
5. AAD binds a ciphertext to its row — swapping ciphertexts between rows fails decryption.

**Master key:** 32 bytes, base64, from `HM_MASTER_KEY` or `HM_MASTER_KEY_FILE` (Docker secret).
The service **refuses to start** without it. Lose it → all stored tokens are unrecoverable (document this for operators).

**Rotation:** `HM_MASTER_KEYS=1:<b64>,2:<b64>` (or `HM_MASTER_KEYS_FILE`) holds versioned keys; a single `HM_MASTER_KEY`
is version 1. New secrets use the highest version; every listed version can open. `hetzner-monitor keys rotate` re-wraps all
DEKs with the newest version; secrets themselves are not re-encrypted and no Hetzner access is needed. The service refuses
to start if the database holds a version that is not configured. In the SaaS, step 3 moves to a KMS/Vault.

Runbook (Docker Compose; keys go into `deploy/.env`, never into a shell history or chat):

1. `hetzner-monitor master-key generate` → new key. Replace `HM_MASTER_KEY=<old>` by `HM_MASTER_KEYS=1:<old>,2:<new>`.
2. Restart **every** process (`docker compose … up -d`) — a process that only knows version 1 cannot open version 2 rows.
3. `docker compose -f deploy/docker-compose.yml run --rm app keys rotate` → prints counts; `keys status` must show only version 2.
4. Optional: drop the old key (`HM_MASTER_KEYS=2:<new>`) and restart. Keep a backup of the old key until a database
   backup taken after step 3 exists — older backups still need it.

## Token handling

- Decrypt only in memory, right before use; zeroize after (`zeroize` crate).
- Never returned by the API — only `token_hint` (last 4 chars).
- On connect: validate with one `GET`. Write permission cannot be detected without a write call, so the UI must state clearly that a **Read** token is sufficient and recommended.

## Authentication

- **PWA:** `POST /api/v1/auth/login` sets `hm_session` (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` unless `HM_BASE_URL`
  is `http://`). Sessions are stored server-side as `SHA-256(token)` so they are revocable. **No JWT.** Lifetime 30 days,
  idle timeout 14 days; logout, password change/reset, disabling the user or removing the membership ends them.
  A session's scope follows the role: `owner`/`admin` → `admin`, `member` → `write`.
- **CSRF:** cookie requests other than `GET`/`HEAD`/`OPTIONS` need `X-CSRF-Token`, the value login and `GET /me` return
  (`base64url(SHA-256("hm-csrf:" || session token))`, derived, not stored) → otherwise 403 `csrf_failed`. An
  `Authorization` header always takes precedence over the cookie.
- **Headless / CLI / Tauri:** API keys `hm_<prefix>_<secret>` as `Authorization: Bearer`, scopes `read | write | admin`. Only a SHA-256 hash is stored; the full key is shown once.
- Passwords: Argon2id (m=19 MiB, t=2, p=1), 12–1024 characters. Unknown users cost the same as wrong passwords (dummy
  verify) and get the same 401. Initial/reset passwords are generated by the CLI and printed once; users without a password
  can set one with an `admin` API key (`PUT /me/password`).
- Login throttling (in-process, 15-minute window): 10 failures per e-mail or 30 per peer address → 429 `too_many_attempts`.
  `X-Forwarded-For` is not trusted, so behind a reverse proxy the address limit is shared. TOTP/OIDC after MVP.

## Web UI

Implemented in M6a ([ADR-0015](../adr/0015-web-ui-embedded-in-binary.md), [web](web.md#serving-and-headers)). The UI is
served by the binary on the API's origin, so the `SameSite=Lax` cookie and the CSRF header work without CORS.

- Every UI response carries `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self'; font-src 'self'; connect-src 'self'; manifest-src 'self'; worker-src 'self'; object-src 'none';
  base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, plus `X-Content-Type-Options: nosniff` and
  `Referrer-Policy: same-origin`. No inline scripts or styles, no `eval`, no `data:` URLs; the app cannot be framed.
- **No third-party requests:** fonts and icons are bundled; the UI talks only to its own origin.
- The **CSRF token is kept in memory only** (never in `localStorage`, `sessionStorage` or a readable cookie) and is
  re-read from `GET /me` after a reload. The session token itself stays in the `HttpOnly` cookie, out of reach of scripts.
- A 401 clears the in-memory token and the cached data and returns to the login form.
- The service worker caches only the app shell, never API responses, so no alert, project or channel data is stored by
  the browser outside the page's memory.
- Secrets are never displayed: Hetzner tokens and channel configs are write-only; a new API key is shown once.
- Web Push (M6b): the browser's push subscription goes to the server once and is never read back; the UI keeps only the
  server-side subscription id in `localStorage` (to mark "this device"). The service worker opens only same-origin
  paths from a push message. Push and service workers require a secure context, so phones need HTTPS (README).

## Web Push

- **VAPID key:** one P-256 key pair per installation, generated on first use and stored in `vapid_keys`, sealed with
  AAD = row id; `keys status|rotate` cover it. Only the public key leaves the server (`GET /push/config`). It is never
  configured or logged. Deleting the row creates a new key on the next start and invalidates every subscription.
- **Subscriptions:** endpoint (a capability: whoever has it can push to the device) and the `p256dh`/`auth` keys are
  sealed as one JSON secret (AAD = subscription id). The API shows the push service host and a name only. A removed or
  expired subscription keeps a tombstone without ciphertext (`deleted_at`) for the delivery history, purged after 90 days.
- **Messages** are end-to-end encrypted for the browser (RFC 8291, a fresh ephemeral key and salt per message); the push
  service sees only the ciphertext, `TTL`, `Urgency` and the VAPID token (12 h, `aud` = push service origin, `sub` =
  `HM_VAPID_SUBJECT`). The payload holds what other channels show: title, alert message, project name and the alert path.
- **Outbound:** pushes go through the same guarded HTTP client as webhooks (SSRF guard, no redirects, no proxy,
  timeouts). `POST /push/subscriptions` accepts only `https://` endpoints; errors are short fixed strings.

## Authorization

Role per membership: `owner | admin | member`. Every handler resolves the caller's `org_id` first and passes it to repositories (tenant isolation, invariant 5).

## Outbound requests (SSRF)

Webhook/ntfy URLs and push subscription endpoints are user-controlled. With `HM_ALLOW_PRIVATE_TARGETS=false` (to be the SaaS default) the notifier refuses
targets in private, loopback, link-local (incl. `169.254.169.254`), CGNAT, unspecified, multicast, reserved and
unique-local ranges, also IPv4-mapped and NAT64 forms: IP literals are checked directly, host names through a DNS resolver
that drops such addresses for every connection (so rebinding between check and connect does not help). Redirects are never
followed and proxies are not used. Self-hosted default: `true` (alerts to a LAN ntfy or webhook are common).
Implemented in `hm_notify::guard` (M4).

## Redaction

- Secret types implement neither `Debug` nor `Display` with real content (`Secret<T>`, `MasterKey`, `Keyring`).
- Passwords, session tokens and CSRF tokens are never logged; login logs only the session id, user and org.
- `tracing` fields for tokens/URLs/keys are redacted. Error messages never embed secrets.
- Channel configs (`hm_notify::ChannelConfig`), `SmtpSettings` and the notifier print only their type; delivery errors are
  short fixed strings (`HTTP 404`, `timeout`, …) built without the URL, so `last_error` and the test endpoint never leak
  a webhook URL, token, secret or recipient. Configs are sealed with AAD = channel id. Push subscriptions and the
  VAPID key print as `[REDACTED]` (`Subscription`, `Vapid` show no endpoint or private key).
- Reported security issues: see [SECURITY.md](../../SECURITY.md).
